# When something goes wrong

Hit the encoding bug below in the wild once - [The encoding bug postmortem](encoding-bug-postmortem.md) has the full story if you want the detail behind the one-line fix.

| What you're seeing | What's actually going on |
|---|---|
| `SSL certificate verify failed` | Confluence is using an internal cert Python doesn't automatically trust. Export it (browser padlock icon, or `certmgr.msc` if that's not locked down) and point `INTERNAL_CA_PATH` in `confluence_common.py` at the exported file (or set the `CONFLUENCE_CA_FILE` environment variable to its path, no editing needed). Every Python script reads it from there, so it's a one-time fix. Full steps are in that file's comments. |
| `Basic constraints of CA cert marked not critical` | This one's not on you, the org's cert itself is missing a flag Python's SSL library insists on, even though browsers and PowerShell don't care. Quickest fix is switching to the `.ps1` version, which doesn't hit this at all. Or set `VERIFY_SSL = False` in `confluence_common.py` for a short-term test, not something to leave on permanently. |
| `Can't find confluence_common.py` (or `.ps1`) | The script's been copied somewhere on its own. Every script needs the shared `confluence_common` file sitting in the same folder - download the whole repo (see [Getting started](getting-started.md)). If the file IS there and PowerShell still won't load it, see the next row. |
| PowerShell says `confluence_common.ps1` "is not digitally signed" or "cannot be loaded" | Windows has marked the downloaded files as "from the internet". Run `Get-ChildItem *.ps1 \| Unblock-File` once in the folder. |
| `WARNING: Confluence doesn't know who you are` | Your login wasn't used - Confluence let you in as an anonymous visitor, so pages that need a login will be missing. See [Who you're logged in as](extracting.md#who-youre-logged-in-as). |
| `401 Unauthorized` | Wrong username/password, or the org's set up SSO in a way that blocks plain API logins. |
| `403 Forbidden` | Login's fine, you just don't have read access to that particular space. |
| A `401`, or a confusing JSON-parsing error mentioning an unexpected `<` character (`confluence_auth_test.ps1`/`confluence_extractor.ps1` only) | Some Confluence setups log you in via your Windows login automatically (Integrated Windows Authentication) instead of a separate username/password - the `<` means the response wasn't JSON at all, it was an HTML login page the script doesn't know how to handle. Confirmed fix for this exact case: run `.\confluence_auth_test.ps1 -UseDefaultCredentials` first to check (skips the username/password prompts, uses your current Windows login instead), then `.\confluence_extractor.ps1 -UseDefaultCredentials` once that confirms it. PowerShell only - there's no equivalent for the Python scripts. |
| `407 (Proxy Authentication Required)` | Your network needs an authenticated proxy to reach the internet, and PowerShell isn't automatically sending your login the way a browser does. `confluence_auth_test.ps1` and `confluence_extractor.ps1` now offer your Windows login to the proxy automatically on every run, so this should already be handled - if you're on an older copy without that, grab a fresh one. Still seeing 407 after that? The proxy needs something these scripts can't provide (a different login, or doesn't accept your Windows account at all) - that needs sorting out with whoever manages your network. |
| `Could not find a part of the path ...`, partway through extracting, even though the folder it's complaining about is visibly sitting right there on disk | Two separate bugs, both fixed now - grab a fresh copy of the script if you're still seeing this. (1) A page title truncated to fit in a folder name could land right after a space, leaving a folder name with a trailing space - Windows drops that trailing space when the folder's actually created, but the script's own record of the name still has it, so later writes into that folder look in the wrong place. (2) Windows PowerShell 5.1 specific: `cd`-ing into a folder before running the script moves PowerShell's own idea of where you are, but not the lower-level mechanism these scripts use to actually write files, which quietly keeps using wherever the window first opened. Folders get created in the right place, but every file write into them then fails this way. If you hit this on `failures.json` specifically (the summary file listing anything that failed), the page-by-page extraction itself is unaffected - the console summary printed just above that error is still accurate, you just won't get the extra saved copy until you re-run with a fresh script. |
| `python is not recognised` | Python's not on PATH, or your terminal was open before Python got installed. See [Running Python in VS Code](python-in-vs-code.md). |
| PowerShell won't run the script at all | `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`, run as yourself, no admin needed. |
| Running a `.ps1` script itself throws something like `Cannot convert value "..." to type "System.Text.RegularExpressions.Regex"` or `[x-y] range in reverse order`, with garbled characters in the error message | The exact same encoding bug as the row below, just hitting a script file instead of Confluence content: these `.ps1` files now carry a UTF-8 BOM specifically so Windows PowerShell 5.1 always reads them correctly, regardless of the machine's system codepage - without one, a script containing a special character can get silently corrupted on load. If you see this, you've likely got an older copy of the file from before the BOM was added (e.g. copied via email/Slack rather than downloaded fresh, or an old network-share copy) - grab a fresh copy of the script and it'll go away. If you're editing these scripts yourself, run `check_script_encoding.ps1` before committing to catch this before it ships again. |
| Weird garbled characters in the Markdown, e.g. `Â` where a space or accent should be, or `â€™` instead of an apostrophe | An old bug in `confluence_extractor.ps1`: PowerShell decoded Confluence's UTF-8 response as Windows-1252, mangling anything non-ASCII (accents, curly quotes, dashes). Already fixed in the extractor, so new extractions come out clean. For content you already pulled before the fix: run `repair_garbled_text.ps1` (or `.py`) **from the folder that contains your `confluence_export`/`confluence_markdown_export` folders** - it doesn't prompt for a location, it just looks for those two folder names right where you run it from (or pass a path directly, e.g. `-Roots C:\path\to\confluence_export`). It prints exactly which folders it found before doing anything, undoes the mis-decode in place, and backs up each file it touches as `.bak`. Afterwards it does a final health check and tells you if any file still looks garbled - usually because a byte got altered further before this script ever saw it, which makes the original text unrecoverable. When that happens it recommends re-extracting just that page (find its id in `manifest.json`, run the extractor again with that id) - that's a safe-looking guess, not a guaranteed fix, so re-extracting is the better option when it's practical. If you'd rather strip the leftover character instead, run it again with `-Force` (`--force` for the Python version) and type `YOLO` at the prompt - both are required on purpose, so this never happens by accident. Every file it strips this way is logged, with a snippet and timestamp, to `garbled_text_repair_log.json`. |
| `repair_garbled_text` prints a couple of lines then seems to just sit there for ages, especially over a network drive | Usually not stuck - it's reading every file, which genuinely takes a long time on a large export or a slow network share (tested: 5+ minutes for 8000 pages even on local disk, no network involved). It says "Scanning..." before the slow part, then prints `[N/Total] Checking: <file>` for every single file right before reading it - so on a big run, there's always something recent on screen, and if it does ever genuinely hang on one specific file (a stuck network read, a locked file open elsewhere), the last line on screen tells you exactly which one. If you're on an older copy without that, grab a fresh one. Still not clear what's going on? Run it again with `-Debug` (`--debug` for Python) - it breaks that one line into a separate announcement for each actual step (reading, repairing, backing up, writing), each with how long it took, plus the full error detail for anything that fails to read. |
| A converted table looks broken, extra `\|` rows or content spilling out of the table | An old bug: a table cell with more than one paragraph, or a line break in it, produced a real newline in the Markdown, which splits a table row across lines. Already fixed, multi-line cell content now becomes `<br>` instead. No re-extraction needed, just re-run the Markdown converter over your existing `confluence_export`. |
| An image shows up broken after uploading, even though `content.md` references it | An old bug: the Markdown linked to the image by its original Confluence filename, which can differ from what's actually on disk (special characters get replaced with `_` when saved, and two attachments with the same name get a `_2` suffix). Already fixed, the extractor now records both names so the converter can point at the right file. Only fixes new extractions though, since the old filename mapping wasn't recorded before, re-run the extractor (not just the converter) on affected pages to pick it up. |
| `confluence_sharepoint_paste.ps1` says "nothing to do" even though you classified a page as `sharepoint`, a page's one-and-only attachment silently never gets downloaded, or `manifest.json` itself doesn't look like a proper list (`{...}` instead of `[{...}]`) after extracting just one page | An old bug specific to the `.ps1` scripts: PowerShell can silently misread a result set as empty/scalar when it has exactly one item (one page, one attachment, one page landing in a bucket) rather than treating it as a one-item list - the `manifest.json` case is the nastiest version, since a malformed manifest breaks every downstream script, not just one symptom. Already fixed throughout, extracting or converting just one or two pages to try things out now behaves exactly like a full run. |
| A Python converter script crashes with a `JSONDecodeError` reading `manifest.json`, but only when it was extracted with `confluence_extractor.ps1` | An old cross-language bug: on Windows PowerShell 5.1, `Set-Content -Encoding UTF8` adds an invisible marker (a BOM) to the front of the file, which Python's `json` module refuses to read. Already fixed on both sides - the PowerShell extractor no longer adds that marker, and the Python scripts tolerate it either way - so extracting with one and converting with the other now works regardless of which combination you use. |
| Non-ASCII page titles (accents, curly quotes) show up garbled in Excel when you open `page_destinations.csv` | The same class of bug as the "weird garbled characters" row above, just via a different path: Excel needs that same invisible BOM marker to correctly read a UTF-8 CSV, and the Python script writing this file wasn't including it. Already fixed - regenerate the CSV (delete it and re-run the Markdown converter) to get a clean copy. |
